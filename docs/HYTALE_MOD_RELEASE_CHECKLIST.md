# Hytale mod release checklist (evidence from Adaptive Surface 1.0)

This is a reusable **gate sequence**, not a certification for other mods. The observed case is Adaptive Surface 1.0.0 on Hytale 0.7.4. Its final visual check, real historical-save client entry and browser distribution were not completed during the technical handoff. Check the target game's current release and rules again for every new mod.

1. **Freeze the accepted behavior.** Record the accepted candidate, target Hytale version, saved IDs, required visuals and the smallest test that could disprove the planned change. Keep earlier accepted parts stable.
2. **Inventory rights before packaging.** List every PNG, model, atlas, recipe and external source per material. Record the actual grant for redistribution. If native or third-party pixels have no grant, exclude them from the download and determine whether local generation from the user's lawful installation is appropriate. Local generation is a technical design, not independent legal clearance.
3. **Validate the exact downloadable JAR.** Check manifest/plugin identity and game version; diff against the accepted candidate; inventory every entry; exclude harness classes, fixture materials, generated packs, caches, worlds, old asset-bearing JARs and private files. Record a SHA-256 hash and verify it after copying to the publication folder.
4. **Exercise failure paths on copies.** Start from the JAR alone; restart; remove only the disposable fixture's active cache; test missing catalogue/native/historical data and inspect the material report. A failed rebuild must retain an existing working pack. For materials learned during play, select a genuinely new donor, verify the request is durable immediately, close the world while optional background work is delayed, and check that the material is usable after the first restart. Keep unavailable donor requests visible without blocking unrelated ones, and never call an input ready merely because a request was queued. Test ordinary placement, occupied cells, protection and persistence. Keep initial failures in the report even if a retry succeeds.
5. **Treat old saves separately.** A client preflight can reject a missing generated mod before Java starts. Prepare a *new* world copy with an independently verified backup and rollback; preserve saved IDs. A synthetic world plus native server start does not establish real client entry into a historical save. On Windows include long paths in the file hash audit.
6. **Separate evidence levels.** Label reproducible current technical tests, previously recorded tests, user-reported visual acceptance and unverified claims. A previous candidate screenshot must retain its version caption. A native actor does not simulate every real mouse or gamepad action.
7. **Make a bounded release decision.** Use a P0/P1/P2 matrix, document unsupported game versions, world storage modes, other-mod combinations and performance limits. Prepare description, changelog, genuine media, license, NOTICE and checksums without inserting them into the mod JAR unless required. The author's visual review and actual platform moderation/delivery are separate gates.
8. **Keep work and upload areas distinct.** Keep source projects, tests and private evidence in the development area. Copy only approved public files into a versioned publication area; mark the single file to upload as the mod. Never use an unreviewed development build just because its version string matches.
